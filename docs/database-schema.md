# Phase 1 database schema

The Phase 1 user request supersedes the Phase 0 schema proposal. The source of executable schema truth is [001_foundation.sql](../apps/api/migrations/001_foundation.sql). Phase 2 uses `jobs` and `job_stores` for atomic queued job creation; Phases 3 and 4 use the existing lease, retry, error, and `store_enrichments` columns, so no new migration is required. Scoring business logic does not exist yet.

## Tables and keys

- **jobs:** UUID primary key (database-generated by default); statuses queued/running/completed/completed_with_errors/failed; nonnegative total_stores; creation/start/finish timestamps; failure code/reason. Queued jobs have no start/finish time, running jobs require start but no finish, terminal jobs require finish. Timestamp ordering is checked.
- **job_stores:** primary key (job_id, store_id), job FK, six required nonblank source fields; pending/processing/retry_wait/succeeded/failed/skipped states; attempts and per-store maximum, eligibility time, lease token/expiry, last error and creation/update timestamps. Store IDs are case-sensitive and job-scoped.
- **store_enrichments:** primary key (job_id, store_id), a composite FK to the same job_store; three nonnegative NUMERIC(18,2) metrics plus enriched_at. The primary key supplies the requested uniqueness. Decimal metrics remain separate from scores.
- **scoring_configs:** primary key (job_id, revision), job FK, three NUMERIC(18,2) bars; three NUMERIC(5,2) weights; Large/Medium NUMERIC(5,2) thresholds; positive revision and updated_at. Weights are each 0–100 and sum exactly to 100; bars are nonnegative; 0 <= medium_threshold < large_threshold <= 100.
- **store_scores:** primary key (job_id, store_id, config_revision), composite FK to that store's enrichment, composite FK to that job's config revision; NUMERIC(5,2) score bounded 0–100, Large/Medium/Small tier, computed_at. Multiple revisions may coexist without allowing cross-job references.
- **schema_migrations:** infrastructure ledger with migration name primary key, SHA-256 checksum, and applied_at.

Finite precision NUMERIC rejects infinities; explicit NaN exclusions on metric/bar columns and upper bounds on percentage fields reject PostgreSQL's special NaN value. Values with excess fractional precision are rounded by PostgreSQL's typmod: later API validation must reject excess precision before insertion, as planned. Database constraints are not a replacement for later input validation.

## Work and active-job invariants

A unique partial index on the constant 1 where job status is queued or running supplies a single shared active slot. It is enforced even for simultaneous connections; checking for an active row before inserting is insufficient.

Attempt counts stay between zero and max_attempts; the maximum is positive. Processing requires a nonnull token/expiry and at least one claimed attempt. Other states require null lease fields. Retry wait requires a due timestamp and an attempt count between one and max_attempts minus one; other states have no retry timestamp.

Phase 2 creates queued jobs with pending stores, zero attempts, configured maximum attempts, and no lease. Phase 3 changes a queued job to running, claims pending rows with `FOR UPDATE SKIP LOCKED`, increments attempts, and assigns UUID leases. Phase 4 also claims due retry rows, clears their due time, and assigns a new token. Retryable failure checks the same ownership fence before moving to `retry_wait`, persisting the safe error and database-time due timestamp, and invalidating the old lease. Exhausted or permanent failures become terminal. Successful metrics and state still commit atomically behind the running-job, processing-state, token, and database-time expiry fence. Phase 5 adds `jobs.provider_failure_streak`; the watchdog conditionally reclaims expired processing rows, while systemic termination clears every unfinished lease and marks those rows skipped.

## Indexes

- jobs_single_active_idx: uniqueness over both active job states.
- jobs_created_at_idx: newest jobs.
- job_stores_pending_idx: (job_id, created_at, store_id), pending only.
- job_stores_retry_eligible_idx: (job_id, next_attempt_at, store_id), retry_wait only.
- job_stores_expired_lease_idx: (job_id, lease_expires_at, store_id), processing only.
- job_stores_status_idx: (job_id, status, store_id).
- store_scores_tier_idx: (job_id, config_revision, tier, store_id).

Primary-key indexes cover referenced store/config identities. Foreign keys use restrictive defaults; no cascade deletion of domain data is introduced. Test-schema cleanup is isolated from application data.

## Changes from Phase 0

Use job_stores instead of store_work, and store_enrichments instead of enrichment_results. Composite store identity replaces internal work UUIDs. max_attempts belongs to job_stores. queued and skipped are included exactly as requested.

No enrichment_attempts table, raw JSON payload, run-settings snapshot, failure-streak counter, or published-config pointer is added in this phase. These were earlier design proposals, not prescribed Phase 1 fields. Future phases must reconcile the proposal with this schema through explicit migrations. A future atomic config-plus-scores transaction could use the highest committed revision as the published revision without a pointer; no such publication logic exists now.

Configuration rows are keyed by revision rather than overwriting one config per job. Scores reference that exact same-job revision. This preserves the planned separation and reproducibility without implementing recalculation.

## Migration safety

The runner uses one pg client for the advisory lock and each transaction. It records a checksum only after the migration SQL succeeds in that transaction, serializes competing migration invocations, skips already-applied unchanged files, and rejects changed/missing migration history. Applied SQL files are immutable; add numbered forward migrations. The generic application transaction helper likewise uses one checked-out connection and rolls back before releasing it.
